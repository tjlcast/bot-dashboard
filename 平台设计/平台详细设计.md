# Agent Control Plane — 平台详细设计（V1）

## 1. 产品定位

这是一个面向单一使用者的 **Agent 工作流控制面**：将多设备、多 App、多会话中的 Agent 汇报收敛为可观察、可介入、可回溯的任务链，而不是替代原生对话工具。

核心体验是「先处理需要人的事，再理解任务全貌」。默认进入时，用户能同时看到：

- 当前最需要介入的任务；
- 被选任务的完整汇报 DAG；
- 选中节点的输入、结论和原始会话来源。

## 2. 信息架构

```text
工作台（默认）
├── 汇报链画板：单链聚焦、缩放/平移、DAG 分叉
├── 详情抽屉：节点全文、来源、介入操作、回到原会话
└── 链列表：排序、待介入开关、设备/App 来源

收件箱
└── 所有 blocked / 需要确认 / 审批 / 输入项，按紧急度处理

接入
└── 设备配对、Watcher、MCP、Token 与接入健康度

设置
└── 通知、保留策略、Token 撤销
```

V1 只需实现「工作台 + 收件箱 + 接入」。不把成本、组织、多人权限等信息塞进首页。

## 3. 默认工作台

### 3.1 三栏结构

| 区域 | 宽度/行为 | 内容与作用 |
| --- | --- | --- |
| 左侧导航 | 64px 收起 / 216px 展开 | 工作台、收件箱、接入；底部展示实时连接状态 |
| 主画板 | 自适应、最小 560px | 当前选中 trace 的 DAG；时间从左至右，分叉上下展开 |
| 右侧链列表 | 320px，可收起 | 所有 trace，默认最近活跃；待介入开关置于排序之前 |
| 详情抽屉 | 从画板右缘覆盖 420px | 点击节点打开，不挤压画板；窄屏转为全屏页 |

画板默认只展示一条链，避免把多条 DAG 同屏铺开造成的认知噪声。未选中的链只存在于右栏；切换链时保留上一次的缩放位置。

### 3.2 节点与连线

- 节点只显示：类型图标、一句话摘要、相对时间和状态。卡片最大两行，禁止放全文。
- `report` 使用中性色；`checkpoint` 为低饱和蓝；`decision` 为低饱和紫；`blocked` 为琥珀色并带清晰文字「待介入」。颜色不是唯一编码。
- 分叉自父节点向上下展开；失败重试分支用「重试」文字而非红色连线。
- 被选节点加深边框与轻微底色；节点详情统一进入抽屉，不在画板上弹大卡片。
- 实时新节点在对应节点旁出现短暂「新」标记；若不在当前链，仅刷新右栏时间和未读点，不强制跳转视图。

### 3.3 右侧链列表

每一项只保留：状态点、任务标题、来源（设备 · App）、最新摘要、最后活跃时间。列表操作顺序：

1. `仅待介入` 开关：默认关闭，但检测到 blocked 时在顶部给出数量提示；
2. 排序：最近活跃（默认）/ 待介入优先 / 最近创建 / 按来源分组；
3. 选择链：切换主画板并将最近的待处理节点作为默认选中节点。

## 4. 节点详情与介入

详情抽屉按阅读顺序组织：

1. 状态和节点标题；
2. AI 结论（默认展开，优先阅读）；
3. 用户输入/上下文（可折叠）；
4. 来源信息：设备、App、session、时间、接入方式；
5. 操作：`介入并发送`（主按钮）、`标记已处理`、`打开原始会话`。

点击「介入并发送」打开轻量回复框，内容发送到该 Agent 的 inbox；发送后该节点转为「已回复，等待 Agent」，并在 DAG 中附加一个 intervention 记录节点。原会话无法深链时，明确显示「此来源暂不支持跳转」，不展示失效按钮。

## 5. 收件箱

收件箱不是另一份任务列表，而是所有人工动作的队列。每项必含动作语义：

| 类型 | 首要操作 | 示例 |
| --- | --- | --- |
| 需要确认 | 确认 / 拒绝 | 「允许修改生产配置吗？」 |
| 需要选择 | 选择方案 | 「选 A：低成本；或 B：低延迟」 |
| 需要补充 | 回复输入 | 「请提供目标地区」 |
| 阻塞升级 | 介入并发送 | 「缺少 GitHub 凭据」 |

队列默认按紧急程度、阻塞时长和最近活动排序。完成动作后保留在历史中，但不再出现在待处理队列。

## 6. 接入与状态

接入页以「一台设备、一种连接」为最小单元，展示在线状态、上次上报时间、App、接入档位。

- A 档：Watcher 监听本地日志并上报；
- B 档：MCP 显式上报，可携带 `trace` 与 `parent`；
- C 档：标记为盲区或手工导入，不在 V1 实现自动采集。

Onboarding 使用一个临时配对码：`pair <code> --name "MyMac-Codex"`。Token 仅本地保存，平台提供撤销入口；连接断开时，在接入页与相应链来源处显示弱提示，不干扰工作台。

## 7. 数据与实时规则

建议的数据层遵循文档中的统一模型，并补齐 UI 所需状态：

```text
Trace: trace_id, title, source_summary, created_at, last_activity_at,
       pending_count, node_count
Node:  node_id, trace_id, parent_node_id, node_type, status,
       device_id, app, session_id, timestamp, title, detail,
       input, conclusion, source_url
Intervention: intervention_id, node_id, body, status, sent_at, replied_at
```

- `trace_id = hash(device_id + app + session_id + local_trace_seq)`；
- B 档优先使用 Agent 显式 `trace / parent`，A 档回退为按 session 聚合；
- SSE/WebSocket 事件只做增量更新：当前 trace 更新节点和布局，其他 trace 只更新右栏；
- 同一事件重复到达必须按 `node_id` 幂等去重。

## 8. 视觉与交互原则

- 风格：近白/深墨中性色为底，使用单一蓝色作主操作；橙色只表示待介入，避免「五彩仪表盘」。
- 密度：页面最多一个主动作；画板内容留白优先于堆叠统计卡。
- 字体：14px 正文、12px 元信息、20px 页面标题；数字与时间使用等宽数字。
- 动效：节点新增、抽屉出现和画板切换采用 160–220ms 过渡；不循环、不用装饰动画。
- 可访问性：状态必配文字/图标；键盘可在链、节点、详情操作间顺序导航；画板提供「线性列表」替代阅读方式。

## 9. V1 边界与优先级

P0：单链 DAG、右栏排序、节点详情、blocked 收件箱、实时增量、原会话回链。

P1：MCP inbox、介入记录节点、设备配对与接入健康度。

暂不做：多人协作、项目/组织管理、成本分析、跨链依赖图、C 档浏览器自动采集。

## 10. 技术架构与部署

### 10.1 架构决策

V1 采用单机、单后端实例。各设备上的 watcher 或 Agent 客户端**直接通过 HTTPS 调用后端**；不在前面增加 Nginx、API Gateway 或消息队列。Dashboard 同样直接调用 API，并订阅后端的 SSE 事件。

```text
Codex / WorkBuddy / Watcher ─┐
其他设备上的 Agent 客户端     ├── HTTPS ──> Fastify API ──> SQLite 文件
Dashboard（浏览器）          ┘                  │
                                                └── SSE：节点/状态增量事件
```

这不是让客户端直连 SQLite：所有鉴权、校验、写入和实时推送均由 API 完成。SQLite 数据文件与 API 进程必须位于同一台主机的本地持久化磁盘，不能放在网络共享盘中。

### 10.2 技术栈

| 范围 | 选型 | 责任 |
| --- | --- | --- |
| Dashboard | Next.js + React + TypeScript | 页面、详情抽屉、收件箱、接入管理 |
| 组件与样式 | Tailwind CSS + shadcn/ui | 现代且低噪声的基础组件与主题 |
| DAG 画板 | `@xyflow/react` + Dagre | 缩放、平移、选择；将单 trace 自动排成从左到右的树 |
| API | Fastify + TypeScript + Zod | HTTP 上报、查询、单 token 鉴权、SSE |
| 数据访问 | Drizzle ORM | schema、迁移、类型安全查询；为未来切换 PostgreSQL 保留余地 |
| 数据库 | SQLite + `better-sqlite3` | V1 的持久化、查询与备份 |
| 测试 | Vitest + Playwright | API/schema 单测与关键用户流程端到端测试 |
| 本地/单机运行 | Docker Compose | API、Web 和本地挂载的 SQLite 数据卷 |

不引入 Redis、Kafka、WebSocket、Nginx 或微服务。SSE 足以将后端已提交的增量同步至浏览器；后续只有出现多 API 实例或高并发写入时，才补 Redis Pub/Sub 与 PostgreSQL。

### 10.3 运行参数

应用启动时对 SQLite 执行：

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

- 所有写入事务必须只包含必要的 insert/update，不能在事务内执行网络调用或 LLM 调用；
- 事务提交成功后才向 SSE 广播事件；
- 后端保持一个 API 副本，SQLite 文件挂载到例如 `/data/agent-control-plane.db`；
- 每日生成可恢复备份，并在升级迁移前自动备份；
- WAL 是并发读写优化，不意味着允许多写入者同时提交；发生 `SQLITE_BUSY` 时，API 进行短暂有限重试并返回可识别错误。

### 10.4 目录结构

```text
apps/
  web/                    # Next.js Dashboard
  api/                    # Fastify HTTP API 与 SSE
packages/
  contracts/              # Zod schema、事件类型、API DTO
  db/                     # Drizzle schema、迁移、SQLite 连接
  ui/                     # 可选：跨页面组件
infra/
  docker-compose.yml
  Dockerfile.api
  Dockerfile.web
data/                     # 运行时卷；不提交 Git
```

## 11. HTTP API 设计

### 11.1 鉴权与约定

- 客户端上报统一使用 `Authorization: Bearer <device-token>`；token 数据库存储摘要，不存明文。
- token 与设备绑定，可独立撤销；上报时校验其 `device_id` 是否匹配。
- 每次上报必须携带 `Idempotency-Key: <uuid>`；相同 token 和 key 在 24 小时内只写入一次，重复请求返回最初结果。
- API 路径统一为 `/v1`，内容类型为 `application/json; charset=utf-8`，时间使用 RFC 3339 / UTC。
- Dashboard 登录态与设备 token 分离。Dashboard 使用单用户 session cookie；浏览器的 SSE 使用同源 cookie，避免把长期 token 放进 URL。

### 11.2 上报节点

```http
POST /v1/reports
Authorization: Bearer <device-token>
Idempotency-Key: 7642bf4a-a4e8-4854-a0f6-8a353969d559
Content-Type: application/json
```

```json
{
  "app": "codex",
  "sessionId": "session_123",
  "localTraceSeq": "marketing-site",
  "parentNodeId": null,
  "nodeType": "blocked",
  "title": "确认品牌主色",
  "detail": "信息架构和桌面端布局已完成。",
  "input": "请在冷静蓝和暖橙中选择。",
  "conclusion": "等待你的选择后继续。",
  "occurredAt": "2026-11-12T02:06:00Z",
  "sourceUrl": "codex://session/session_123"
}
```

后端从 token 推断 `device_id`，生成或查找：

```text
trace_id = hash(device_id + app + session_id + local_trace_seq)
node_id  = trace_id + 节点序号（或 UUID）
```

成功响应为 `201 Created`，返回 `traceId`、`nodeId`、`createdAt` 与规范化 `status`。`parentNodeId` 存在时必须属于同一 `traceId`；否则返回 `422 INVALID_PARENT`。同一条显式 trace 可跨会话时，客户端须在请求中额外提供已注册的 `traceKey`，V1 默认不支持任意跨 trace 引用。

### 11.3 查询与实时事件

| 端点 | 用途 |
| --- | --- |
| `GET /v1/traces?sort=recent_activity&pendingOnly=false` | 右栏 trace 列表 |
| `GET /v1/traces/:traceId` | trace 元数据和聚合状态 |
| `GET /v1/traces/:traceId/nodes` | 画板 DAG 节点与边 |
| `GET /v1/nodes/:nodeId` | 详情抽屉全文与来源 |
| `POST /v1/nodes/:nodeId/interventions` | 向 Agent inbox 提交人工回复 |
| `PATCH /v1/interventions/:id` | 标记已送达/已回应/关闭 |
| `GET /v1/inbox?status=pending` | 待人工处理队列 |
| `GET /v1/events` | SSE 增量事件流 |
| `POST /v1/devices/pair` | 使用配对码创建或更新设备 token |
| `GET /v1/devices` | 接入页与健康状态 |

SSE 事件只传递足以局部刷新的数据：

```text
event: node.created       data: { traceId, nodeId }
event: node.updated       data: { traceId, nodeId, status }
event: intervention.created data: { nodeId, interventionId }
event: device.updated     data: { deviceId, state, lastSeenAt }
```

前端收到事件后以对应查询端点拉取最新实体；不把完整详情直接塞入事件，降低断线重连与版本兼容成本。SSE 支持 `Last-Event-ID`，断线后服务端按事件流水补发，补发窗口过期则前端重新拉取当前列表和选中 trace。

### 11.4 错误格式

```json
{
  "error": {
    "code": "INVALID_PARENT",
    "message": "parentNodeId 不属于当前汇报链",
    "requestId": "req_..."
  }
}
```

使用：`400 VALIDATION_ERROR`、`401 UNAUTHORIZED`、`403 DEVICE_MISMATCH`、`404 NOT_FOUND`、`409 IDEMPOTENCY_CONFLICT`、`422 INVALID_PARENT`、`429 RATE_LIMITED` 和 `503 STORAGE_BUSY`。日志、响应和事件都包含 `requestId` 便于排错。

## 12. 数据库设计

### 12.1 核心表

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `devices` | `id`, `name`, `token_hash`, `state`, `last_seen_at` | 每台接入设备 |
| `traces` | `id`, `source_key`, `title`, `created_at`, `last_activity_at`, `pending_count` | 一条任务/工作流 |
| `nodes` | `id`, `trace_id`, `parent_node_id`, `node_type`, `status`, `title`, `detail` | DAG 节点 |
| `node_content` | `node_id`, `input`, `conclusion`, `metadata_json` | 可能较大的正文与扩展数据 |
| `interventions` | `id`, `node_id`, `body`, `status`, `sent_at`, `replied_at` | 人工介入和 Agent 回执 |
| `idempotency_keys` | `token_id`, `key`, `response_json`, `expires_at` | 防止重复上报 |
| `event_log` | `id`, `type`, `payload_json`, `created_at` | SSE 重放窗口 |

`nodes.parent_node_id` 外键指向 `nodes.id`。写入时由应用层验证父子节点同 trace；SQLite 不使用递归触发器维持业务规则。

### 12.2 必要索引

```text
traces(last_activity_at DESC)
traces(pending_count DESC, last_activity_at DESC)
nodes(trace_id, occurred_at ASC)
nodes(parent_node_id)
nodes(status, occurred_at DESC)
interventions(status, created_at ASC)
idempotency_keys(token_id, key) UNIQUE
event_log(id)
```

正文内容默认存为 `TEXT`；仅不稳定的接入来源元数据、原始 payload 存为 SQLite JSON 文本。将需要排序/筛选的字段显式建列，避免把核心查询依赖在 JSON 解析上。

## 13. 关键流程

### 13.1 客户端上报

1. 客户端将本地日志或 MCP 事件归一化为 `ReportInput`。
2. 发送 `POST /v1/reports`，携带设备 token 和幂等键。
3. API 校验 token、schema、父节点、事件大小和速率限制。
4. 单个短事务内创建/更新 trace、写入 node、更新 `pending_count`、写入 event_log。
5. 事务成功后向 SSE 连接广播简短事件，响应 `201`。
6. Dashboard 局部刷新当前画板或右栏；不主动抢占用户正在查看的其他 trace。

### 13.2 人工介入

1. 用户在画板节点详情或收件箱选择「介入并发送」。
2. 前端 `POST /v1/nodes/:nodeId/interventions`，后端写入 intervention 并创建审计节点。
3. Agent 按轮询 inbox 或后续长连接取得指令；收到后回传确认节点。
4. 当 Agent 给出回应或任务恢复时，原 blocked 节点转为 `resolved`，收件箱自动移出该项。

## 14. 安全、容量与可运维性

- API 仅暴露 HTTPS；单 token 也必须可撤销、轮换，token 用 SHA-256/argon2 摘要保存。
- 请求体设置上限（建议 256 KB）；大原始日志只保留摘要和可选外部引用，避免 SQLite 文件被无界增长。
- 按 token 设置上报频率限制；超限返回 `429`，客户端使用指数退避重试。
- SQLite、WAL 文件和备份必须使用同一持久化磁盘；备份采用 SQLite 在线备份 API 或一致性快照，不直接复制活跃 WAL 中的主库文件。
- 提供 `/healthz`（进程活跃）和 `/readyz`（可读写 SQLite）端点；接入页展示每个设备的最近心跳。
- 日志使用结构化 JSON，所有写请求携带 `requestId`；敏感正文不得写入常规访问日志。

## 15. 实施顺序与升级条件

### V1 实施顺序

1. 建立 `contracts`、SQLite migration、`POST /v1/reports` 与幂等写入。
2. 实现 trace 列表、单 trace DAG 和节点详情读取。
3. 增加 SSE 与 Dashboard 增量刷新。
4. 实现 blocked 收件箱、intervention 记录与设备配对。
5. 补齐备份、健康检查、端到端测试和 Docker Compose。

### 从 SQLite 升级至 PostgreSQL 的触发条件

- 需要同时运行多个 API 实例；
- 写入事务持续排队、频繁出现 `SQLITE_BUSY`，且短事务与重试无法消除；
- 需要跨机器部署数据库或高可用；
- 原始内容、审计与检索规模使单库文件的备份恢复窗口不可接受。

升级时保留 HTTP 契约、Zod schema、Drizzle 表结构和前端查询模型；仅替换 `packages/db` 的驱动与迁移配置。
